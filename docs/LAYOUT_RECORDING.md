# 主动布局、习惯与回放

点击「整理桌面」后，Smart 先分析各显示器上的遮挡、标题栏可操作范围，以及共同阅读和轮换使用的证据。近期切换、两窗当前的可见程度和用户设置可以影响同一种摆法的得失。保守档搜索局部修复，平衡档搜索相关窗口的重排，积极档进一步尝试整屏布局。候选方案与现有桌面一起评分，固定遮挡、尺寸限制与受保护的内容区域参与检查。

候选生成会根据屏幕上的实际遮挡矩形寻找连续空位。例如，屏幕中间有固定窗口时，也会尝试在左侧完整走廊里分行摆放一组窗口，或把一扇被挡住的窗口移进最近的空位。跨屏窗口在两块屏幕上实际覆盖的区域都计入遮挡。连续空位搜索参考 Bell 与 Feiner 的[动态空间管理](https://hci.stanford.edu/courses/cs448b/papers/BellFeiner_uist00.pdf)。

最近搭档按两扇窗各自的切换量衡量直接来回切换的强度。常被多个任务打开的窗口以及证据接近的多个候选会降低确定性。这个判断参考 [Taskposé 的窗口切换比例](https://hci.stanford.edu/publications/2008/taskpose/taskpose-uist08.pdf)。如果设置允许主副窗交叠，评分只减免相邻侧边内的遮挡，重叠范围之外的内容和其他窗口造成的遮挡照常计算。

焦点按窗口实例在内存中记录。整理会分别看前台、停留、最近的点击或滚动，以及与当前窗口来回切换的强度。离焦通常按 12 秒半衰期降权。当新窗口已持续在前台并仍有输入时，缺乏新操作的旧窗口按 5 秒半衰期降权。首次打开独立窗口时，前一个实际使用的窗口或新窗口的所属窗口可以暂时成为返回入口。后续的停留、操作和反复切换会更新这个判断。播放和画面变化可提供局部监看线索。

完整辅助和自动整理会在短时间内保留刚完成的手动摆放。选布局时，会先保护当前任务已有的可读内容和可用尺寸，再比较对齐和空间利用。快照与整理日志按会话内窗口编号记录每项注意力信号和手势约束，供诊断和回放。

两扇已确认的任务窗口严重重叠时，保守档也会搜索原尺寸的空位。这个候选只平移被遮挡的一扇，前面的窗口和其他任务窗口保持原位。

默认求解器使用当前工作区和 DPI 计算目标尺寸，优先保障主窗可读、参考窗能看清、返回窗口可点。它在内存中尝试平移、扩容、邻窗让位等组合，比较最终布局后再请求调整。三档强度决定每次搜索的范围和舒适尺寸。

在「数据与记录」中开启记录即可积累手动样本。「智能整理时参考已记录习惯」控制整理时是否采用样本。稳定拖动后，记录移动窗口在工作区中的相对位置、宽度、与搭档的左右关系，以及移动是否露出了搭档的一小块区域。用户手动改变高度时，也会记录该窗口占工作区的高度比例。多次独立的缩放可以形成高度偏好。同一应用组合在同一屏幕类型的半小时内只贡献一票。拖动副窗时也记录主窗的相对位置与宽度，两个方向的手动操作按时段去重。跨会话偏好至少需要三个独立时段的支持。近期样本权重较高。一次动作跟在自动整理之后只作为时间关联记录。横向移动、手动改宽、手动改高分别计票；仅移动窗的位置或挪动其搭档，不会把当时看到的大小变成首选宽度。若两种摆法互相冲突而证据相当，当前轴继续使用默认模型。旧样本仍可用于位置，旧的已导出决策保留当时的回放语义。同一显示器上有多个相同应用身份的窗口时，跨会话模型跳过无法区分的移动窗或搭档。跨会话应用键由本机密钥、进程路径和窗口类生成。窗口实例随销毁事件退役。

一次手动调整有两个位置可供分析：松手的位置和随手辅助后的实际位置。记录中 `assisted-release` 表示一次可归因于随手辅助的调整已经核实；个人摆放模型学习用户的松手位置。跨屏、系统自行改变和后续被打断的调整不作为持久摆放样本。单窗习惯与有搭档时的左右位置分开累计。

在完整辅助或自动档启用个人习惯时，同一程序的两扇窗也可以在本次会话中各有自己的位置。重复的手动摆放至少相隔两分钟，方向一致时会产生短期偏好。它按 45 分钟半衰期衰减。窗口销毁后，新窗口取得新编号。暂停长期记录时，当前任务仍可使用这份内存偏好；写入跨会话样本需要开启记录。

## 导出字段

「当前快照」独立于长期记录。默认在内存中每秒采集一次窗口位置和状态，并保留最近 60 秒的整理请求及实际落位。点击后继续采集约 10 秒。快照 ZIP 的 `timeline.jsonl` 中，`ElapsedMs` 以点击为零，负数表示点击前。`layout-decisions.jsonl` 同时包含点击前后捕获的决策，`summary.txt` 分别列出数量。刚启动时只会导出已有的历史，关闭「快照追溯记录」会立即清空缓冲区。

| 文件 | 如何解读 |
| --- | --- |
| `workspace-*.jsonl`、`adjustments-*.jsonl` | 会话内窗口编号、显示器边界与工作区、DPI、窗口矩形、层级、前台状态和可调整尺寸。拖动包含起止和稳定后快照。可见率以整个窗口为分母，另存屏幕外比例、最大矩形碎片和行优先的 4×4 可见率。十六进制 F 表示整格可见。透明、非矩形表面和录制器没有枚举的窗口会带来误差。 |
| `activity-*.jsonl` | 每约 5 秒采样。按 `Session + GeometryTick` 找几何快照，几何变化或约一分钟写入一次完整快照。每窗保存前台或后台可见时长估计，同一采样内的窗口可计算共同可见时间。两端状态不同、桌面锁定或采样中断时，相应时段未知。锁屏判断依赖当前输入桌面。进程实例共享 CPU（核数）与工作集（字节）。 |
| 画面与媒体证据 | 可选画面变化采样每次最多读 8 个可见应用窗口（含全屏和最大化窗口）。比较位置稳定且前后完全可见的网格，输出可比较与发生变化的两个位掩码，零和未知分别记录。媒体状态归属来源应用。连续两次变化才参与活动推断；覆盖面积、前后台与进程资源提供「类似游戏交互」「后台动态」「局部动态」等弱标签。直接观察不到注视、最小化驻留或哪一个浏览器标签页在播放。 |
| `plans-*.jsonl` | 由 `Session + RequestId` 关联整理前快照、候选代价、同一评分阶段的默认选择（BasePlan）及个性化选择（ScoredPlan）、视频修正后的最终提案（Proposal）、系统接受的目标和稍后实测的结果。`AfterRequest` 把 30 秒内开始的后续手动调整关联到对应窗口上一次布局。不同的手动操作可能恰好发生在这个时段。 |
| `placement-v1.json`、`intent-reference.json` | 前者保存最多 1024 个独立摆放样本，评分采用最近 120 天的数据。后者保留原有间距和布局关系参考。安装密钥、原始画面、原始句柄、窗口标题与可执行文件路径不进入导出包。 |

### 使用时长、共同使用和资源归属

活动日志第 6 版每约 5 秒写一行。用 `Session + Tick` 定位采样，用 `Session + GeometryTick` 找同次或先前的完整几何帧。窗口编号只在本次会话内有意义。

| 需要分析的问题 | 字段与计算方法 |
| --- | --- |
| 一个窗口什么时候在前台？ | `Usage.Foreground` 按切换事件把时段拆成 `Id`、`OffsetMs` 和 `DurationMs`，偏移从 `Tick - ObservedMilliseconds` 起算。短暂切到别窗又回来也会拆段。每窗 `FocusEventMs` 为其本时段各段之和。编号 0 是桌面或已排除的界面。锁屏、长采样间隔或实际前台与事件不符时，`Usage` 留空。 |
| 前台停留期间是否有操作？ | `Usage.PointerActions` 按窗口统计实际鼠标按下、滚动及已完成的拖动或缩放事件。一串拖动可产生多个事件。输入监听不可用时此项为 null。结合系统 `InputIdleMilliseconds`、前台时长和后续操作判断使用强度。键盘输入内容与鼠标坐标不会写入此日志。 |
| 哪些窗口常一起用？ | `CoUse` 配对本时段的前台窗和两端都可见且位置稳定的其他窗口。时长取前台窗的事件停留时长。按会话归集重复配对，再查看双向切换、各自可见比例和手动调整。一个前台窗可与多扇副窗同时配对，各对时长不能相加成使用总时长。两端采样无法验证整段持续可见或用户注视。 |
| 内容角色及露出面积如何？ | `Windows.ApplicationRole` 给出识别的应用类别，`ActivityHint` 给出该时刻的媒体、动态或前后台线索。整理时的判定在 `plans.Signals`，包含主副关系、注意力信号、角色和受保护区域。`VisibleRatio`、`LargestFragmentRatio` 分别表示全窗可见比例、最大可见矩形占原窗比例。结合几何帧的 `Exposure.Cells` 和 `LargestFragment` 判断露出的是哪个角。 |
| 多次打开新窗口后，哪些来源在等待？ | 整理记录的 `Signals.Navigation.Hops` 按打开顺序保存各次跳转。每一跳的 `Source`、`Target` 使用本次会话的匿名窗口编号，可与同条记录的 `Before.Windows[].Id` 对照。末跳目标是当前主窗。`SourceRole` 标示直接返回入口（`return`）、等待的祖先（`waiting`），或只观察到了跳转的来源（`source`）。`Evidence` 给出该跳所依据的输入、窗口归属或创建和前台事件。`ObservedAt` 是采集导航状态时的 UTC 时间，减去每跳的 `AgeMilliseconds` 可得到事件时间。整理导出的 `plans-*.jsonl` 和桌面快照的 `layout-decisions.jsonl` 都使用此字段。行为回放的 `NavigationSources` 列出该帧因导航关系而暂停回收的匿名窗口编号。 |
| 视频画面本身能看到多少？ | 存在可信的视频视口检测结果时，`plans.Signals.Video` 记录会话内窗口编号、屏幕坐标下的视口矩形、内容宽高比、检测置信度，以及按视口计算的 `Exposure`。没有视口证据时此项为 null。全窗的可见比例和媒体状态不能直接代表视频画面的可见比例。 |
| 一组同进程窗口占多少内存？ | 按同一行 `Windows.Process` 关联 `Processes.Instance`。每个根进程在该行只计算一次。`OwnWorkingSetBytes` 为根进程当前驻留内存，`OwnPrivateBytes` 为根进程专用提交内存，单位均为字节。`WorkingSetBytes` 包含成功采样的后代进程，`DescendantsRead` 和 `DescendantsConsidered` 标注有界遍历覆盖情况。进程树共享页可能重复计入工作集。比较应用内存时按进程实例去重；无法直接拆出单个窗口的内存。 |

旧版导出可继续用于回放。第 5 版 `ForegroundMs` 使用相邻两次采样的端点估算，能漏掉几秒内往返的任务；只有第 6 版 `FocusEventMs` 使用时段内的前台事件。单次采样的未知字段保持未知。

所有采集和学习都在本机完成。导出的 ZIP 由用户选择是否交给云端模型。建议按会话或日期留出数据，对照默认与个人版本的主副关系、换边、缩放、局部露出、后续手动纠正和撤销。云端可据此提出规则，再通过同一组场景回放。日志滚动上限为 30 天、128 个文件、合计 128 MiB；先达到的限制生效。清空会同时删除日志、个人摆放样本与身份密钥。

在完整辅助中，已知副窗仅剩一条窄边时也可以与当前主窗一起参与评分。手动整理和自动档也考虑被普通窗口完全遮住的窗口。已标记需要保护的动态角落保留位置。窗口实际缩小后停在请求值之上时，先只约束此窗口。两个仍存在的同应用窗口分别出现一致下限后，才会给同类窗口采用该下限。新版整理日志同时记录强度与桌面分析范围，供回放使用。旧日志沿用平衡强度与原分析范围。

## 云端规则与本地应用

在「数据与记录」中打开数据目录即可找到 `compiled-rules.json` 模板。导出的 ZIP 包含当前生效的规则及本文。云端可根据稳定的手动调整提出一份候选 JSON，用本地回放验证后替换同名文件。下一次整理读取新规则。编辑中的无效文件沿用进程内最后一份有效规则；移走文件恢复内置规则。

示例中的两串 24 位十六进制字符代表本机导出包中的 `AppKey`。相同显示器上每个应用键恰好匹配一扇可管理窗口时，这条配对规则才会生效。

```json
{
  "Version": 2,
  "MediaOverlap": 0.31,
  "AudioPeakThreshold": 0.02,
  "FragmentChangeThreshold": 0.08,
  "Pairs": [{
    "FirstApp": "AAAAAAAAAAAAAAAAAAAAAAAA",
    "SecondApp": "BBBBBBBBBBBBBBBBBBBBBBBB",
    "FirstSide": "left",
    "Overlap": 0
  }],
  "RolePairs": [{
    "FirstRole": "game",
    "SecondRole": "media",
    "FirstSide": "left",
    "Overlap": 0.31
  }],
  "AppSlots": [{
    "App": "CCCCCCCCCCCCCCCCCCCCCCCC",
    "Side": "right",
    "Width": 0.30
  }]
}
```

- `FirstSide` 可选 `left`、`right`、`either`。`Overlap` 的范围为 0～0.4，以较窄窗口的宽度为分母。两窗横向拥挤时，对比并排与保留高度的局部重叠方案。`MediaOverlap` 是有媒体证据时的默认候选；可靠的手动配对习惯优先。屏幕足够宽时无需为了重叠而移动两窗。
- `Version` 兼容 `1` 与 `2`。除精确 `AppKey` 配对（`Pairs`）外，`RolePairs` 支持按实时行为角色（`game`、`media`、`passive`、`foreground`、`companion`、`any`）对新安装的游戏或播放器做通用主副排版；`AppSlots` 为单个应用提供缺省侧边（`left`、`right`、`center`）与相对宽度先验，并在手动整理与自动辅助（`FullAssist` / `AutoFullAssist`）中共享。
- 音频与资源采样通过进程父子快照自动向上归集浏览器或启动器子进程的音量峰值（兼容 `AUDCLNT_S_NO_SINGLE_PROCESS`）、CPU 与工作集内存。跨进程共享音频峰值单列为 `SharedAudioPeak`，系统保持显示器开启的请求记为 `DisplayRequired`，两者都不能定位某个窗口。同进程多窗有播放信号时，还需要窗口自身的画面变化才会据此判断媒体角色。暂停记录后，完整辅助与自动完整辅助仅在内存中采样；手动 Smart 整理后最多再采样 20 秒。
- 开启画面变化采样后，如果副窗可见比例低于 25%，从最大可见矩形内取一块最多 160×160 像素的区域，在 16×16 网格上比较。`FragmentChangeThreshold` 指发生变化的网格点比例。连续两个可比较时段达到阈值后，整理保留副窗位置与这块区域。一次采样即使只有十六分之一的窗口可见也能提供证据。锁屏、中断、移动和鼠标落在采样块内会打断比较。每个时段都进入活动日志，即使几何位置不变。
- 新版 `plans` 记录包含该次的规则和匿名决策输入，包括主副窗口、用于匹配角色的活动标签、被保护的区域、已验证的尺寸下限及应用槽位规则之前的个人偏好。缺失标签保持未知。用 `dotnet run --project tests/LayoutModel -c Release -- Recorder.zip candidate.json` 比较候选规则。旧日志缺失的行为线索保持未知；离线回放不包含原生窗口约束及后续视频尺寸修正。
- 分析时按会话留出记录，分别比较遮挡、主窗阅读尺寸、用户换边及整理后手动纠正。先用实际结果检查规则适用的窗口对，再扩大范围。偏好样本记录在本机密钥对应的安装中，清空数据后原有配对键失效。

## 验证

在仓库根目录运行 `dotnet run --project tests/LayoutModel -c Release`。追加 `-- path/to/Recorder.zip [candidate.json]` 可在本地回放手动、拖动手势及桌面变化触发的 Smart 请求，并关联 `adjustments-*.jsonl` 中的 `AfterRequest` 人工二次微调，在有对应手动修正的请求上输出候选规则与修正结果的横向中心/宽度归一化误差（`PostArrangeRegret`）及纵向中心/高度误差（`PostArrangeVerticalError`）。有完整快照和受保护区域时，`ProtectedRegionsPreserved` 给出候选方案能否保住该区域；缺少证据的指标留空。每个请求分别按可缩放和固定尺寸两种假设输出目标位置，旧记录缺少可缩放字段时这两种结果构成敏感性检查。「当前快照」导出的 ZIP 也可以直接传给同一命令。回放使用当时记录的信号，输出的是重新计算的方案。原生窗口实际是否接受调整，可在快照的决策日志中按请求编号查看后续实测结果。

设计依据包括通过窗口切换推断任务关系的 [Taskposé](https://hci.stanford.edu/publications/2008/taskpose/taskpose-uist08.pdf)、对窗口局部进行独立观察的 [WinCuts](https://www.microsoft.com/en-us/research/publication/wincuts-manipulating-arbitrary-window-regions-for-more-effective-use-of-screen-space/)，以及记录应用级播放状态的 [Windows 媒体会话接口](https://learn.microsoft.com/en-us/uwp/api/windows.media.control.globalsystemmediatransportcontrolssession)。评分阈值是本项目的工程选择。

## 行为学习

「行为学习摆放」分别控制本机已学的摆放习惯与导入的摆放规则。「行为学习」处理工具窗口被下一项任务接手后何时退出桌面。开启本地学习时，应用观察跨应用的前台交接、随后出现的关闭或最小化，以及短时间内是否重新出现。同一模式出现三个有效样本后才提供候选规则。每条候选或导入规则由用户独立开启。连续重新打开会放慢或暂停该规则。关闭使用窗口的标准关闭请求，最小化保留后台进程。

开启「数据与记录」后的导出包附带 `SKILL.md`、`layout-guide.md`、两种规则文件和时间线。新增的 `behavior-*.jsonl` 由 `Session + Segment + Tick` 排序，事件包括应用可执行文件名、会话内窗口编号、进程启动时刻、前台、出现、关闭、隐藏、最小化与 WinWindow 发起的动作。观察到的外部变化可能来自用户、应用或系统。录制由用户控制，应用路径、标题和原始句柄仍不加入这份长期记录。

行为候选文件的结构如下。示例中的应用名可以替换为日志中实际出现的名字。

```json
{
  "Version": 1,
  "Rules": [
    {
      "Id": "helper-handoff",
      "Name": "任务接手后收起辅助窗口",
      "SourceApp": "helper.exe",
      "NextApps": ["task.exe"],
      "Action": "Minimize",
      "RequireNewProcess": false,
      "DelayMilliseconds": 3500
    }
  ]
}
```

`Action` 支持 `Minimize` 和 `Close`。关闭需要指定下一项任务。`RequireNewProcess` 要求下一项任务的进程在源窗口获得前台后启动。`DelayMilliseconds` 是下一扇窗持续处于前台时的初始等待，范围 1500～30000 毫秒。开启本机学习后，实际等待时间会随样本调整。外部规则可以在「行为学习」中导入，摆放规则在「行为学习摆放」中导入。

返回来源窗会重新开始一次访问，并重新计算启动与停留时间。切到无关任务会结束此前的交接。窗口仅隐藏或进入托盘时，日志保留实际观察到的状态，学习和回放将其作为动作类型未知的证据。最小化和关闭分别使用各自的窗口状态验证。

用 `dotnet run --project tests/LayoutModel -c Release -- --behavior recordings.zip behavior-rules.json [session]` 回放尚未参与拟合的会话。输出每条触发及观察到的后续结果，包括匹配的收起、迅速回到源窗口、未观察到收起和证据不完整。摆放回放也支持末尾的会话参数。

「当前快照」是独立的排查入口。它从点击时开始连续采集约 10 秒，并在桌面生成 ZIP。包内摘要、时间序列和采集期间的整理决策可用于排查，窗口状态包含标题、位置、DPI、前台、层级、最小化、透明度与显示器边界。


### 手势过程、晚于 30 秒的调整与观察空档

开启布局记录后，导出包里的 `gestures-*.jsonl` 保存逐次手势事件。用 `Session + GestureId` 关联同一次手势，用 `WindowId` 关联会话内的窗口实例。按住后原地松开、只动一两个像素、尚未通过稳定性确认的操作也会留下原始记录。窗口在松手前销毁、失去可用状态，或遇到暂停和退出时，已观察到的开始和结束原因可以保留。单有开始事件时，结束状态未知。

| 记录 | 能分析什么 |
|---|---|
| `start`、`release` 的 `Tick`、`Frame`、`WorkArea`、`Dpi` | Windows 报告的起止时刻与采集时的可见边框。结合两端工作区识别跨屏和 DPI 变化。 |
| `OuterPath`、`OmittedPathPoints` | 根据拖动中的位置事件最多每 100ms 取一个外框位置，相对手势起点记录时间。最多保留 96 点，超出后保留最新点并计数。外框可能包含不可见边距，应分别比较同一口径的坐标。 |
| `Prior`、`Change` | 同一窗口实例最近一次登记的布局请求、请求前和提交的目标框、到这次手势开始的毫秒数，以及有符号的 X、Y、宽、高变化。`ReturnedAxes` 记录哪些曾被系统改变的轴回到了原值附近（3 像素容差）。`StartedAtSubmitted` 可用来判断手动调整开始时窗口是否已经偏离目标。提交是否成功落位应查对应的 `plans.Actual`。 |
| `AutomationMarked`、`DroppedEvents` | 指示当时是否有自动操作标记，以及批次满后丢了多少原始事件。用 `adjustments` 的 `Outcome` 和 `SettledContext` 核对后续状态。 |
| `activity.FocusCoverage`、`focus-*.jsonl` | 保留时间区间、起始前台、实际观测的末端前台、带单调时刻的切换序列、匿名窗口的指针操作次数及漏记计数。可观察 A→B→A。首次采样、采样间断、钩子不可用、事件溢出、末端不一致等情况单独标记。暂停、退出、桌面不可用和导出时的末段写入 `focus` 文件。同一时段的导出截面可能与后续完整区间重叠，聚合时按会话和时刻去重。 |

较晚的调整可以关联到仍存活的同一实例。后续布局覆盖原请求，实例销毁、撤销、暂停、清空和桌面观察重置会结束对应关联。原来的 `AfterRequest` 保留 30 秒口径，稳定性指标继续使用已确认的手势。回放额外列出 `ObservedReleaseDetails`；新字段缺失的旧包表示未知。

点击「当前快照」时，即使日常布局记录已暂停，也会在快照的采集时段观察手势。启用快照回看后还可包含点击前最多 60 秒的手势。窗口内有事件才生成手势文件，快照范围之外的轨迹点和早先布局关联会裁去。日常记录关闭时，这部分手势仅进入快照内存缓冲。详细的前台事件区间随日常布局记录导出。

回放还会汇总实际观察到的手动摆放次数。每轮的 `RecordedManualFollowups` 统计已确认的、同一窗口在关联请求后的手动摆放。`RecordedUndoOfThisRequest` 通过用户撤销的源请求编号关联。整段的 `WithoutLinkedRequest` 是没有关联请求的手动操作，包含开始新任务和独立摆放等情况。快照缺少手势记录时，手势总数留空。时间上相邻的手势可能另有目的；没有后续记录也不足以认定用户满意。对比新旧策略应同时观察手动介入、可读面积、可返回性和布局稳定性。


实际松手辅助若进入原生提交阶段，`plans` 与快照里的 `GestureTiming` 可用于比较预计算和临时求解。`WindowId` 是手动操作窗的会话内编号，`ReusedPreview` 表示松手校验通过、候选集参与了决策。`ReleaseToFirstGeometrySubmitMs` 从 Windows 报告移动或缩放结束的单调时刻计到第一个成功提交的几何操作，`ReleaseToGestureWindowSubmitMs` 只计算被手动操作的那一扇。未发几何请求或该窗未成功提交时，对应字段为空。屏幕实际绘制还取决于目标应用和桌面合成器。验证定时器后续采样的时间不能用来计算首帧到屏延时。
